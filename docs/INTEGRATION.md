# Consumer integration

1. Resolve `@lekoala/map-view/define` and relative dynamic `./providers/*.js` imports through the bundler or importmap. The core keeps the literal `await import()` shape in its loaders: asset pipelines that scan vendored ESM (e.g. Symfony AssetMapper over jsDelivr `+esm` builds) discover lazy dependencies through that form, so do not transpile it away. Map optional bare SDK specifiers explicitly.
2. Load `map-view.css` and the MapLibre SDK stylesheet when applicable. Give the canvas a nonzero block size. Keep responsive layout in the application.
3. Emit points and optional center as JSON data scripts. Put scalar provider settings in attributes. Apply application-specific link restrictions before emitting data.
4. Supply an explicit MapLibre style and optional worker URL, or a restricted Google browser key and map ID. Preserve lazy SDK imports.
5. Test partial navigation, hidden layouts, retry and zero SDK/style/tile requests before activation in the consuming application.

For Symfony AssetMapper/importmap: `importmap:require @lekoala/map-view/define` downloads the jsDelivr `+esm` build, whose provider and SDK imports are rewritten to `/npm/…` URLs. Because the loaders use the literal `await import()` form, the resolver discovers and vendors the providers and their SDK imports (`maplibre-gl`, `@googlemaps/js-api-loader`) recursively as importmap entries. Downloading into the importmap is not browser loading: the imports stay dynamic and no provider or SDK code executes before activation. With the Symfony 8.2 `--no-esm` option the internal relative files are downloaded automatically, but bare SDK imports are not resolved: require the SDK packages explicitly, including a browser-usable MapLibre worker file for the MapLibre adapter and a browser-compatible loader build for Google. This repository does not include or claim a framework-specific integration test. Consumer applications should validate their own asset configuration; these fixtures are outside the package release gate. Application migrations belong in their own repositories.
